Employee API con curl

Cinco verbos HTTP, seis rutas y ningún cliente gráfico. Vas a levantar la API de empleados, mandarle peticiones a mano desde la terminal y leer lo que responde — que es exactamente lo que hace Postman por debajo.

  • ~30 min
  • Java 21
  • MySQL 9.7 en Docker
  • localhost:8080

Paso uno

01 Requisitos

Antes de mandar una sola petición, comprueba que tienes las cuatro piezas. Cada línea de abajo trae el comando que lo verifica: si alguno no responde lo que esperas, resuélvelo antes de seguir.

  • [ ]Java 21 o superior java -version debe decir 21 o más. La app no arranca con 17.
  • [ ]Docker corriendo con MySQL docker ps debe listar el contenedor mysql-9.7 con estado Up.
  • [ ]curl instalado curl --version. Ya viene de fábrica en macOS, Linux y Windows 10 en adelante.
  • [ ]jq (opcional pero muy recomendable) jq --version. Formatea el JSON para que sea legible.

# crear el contenedor (solo la primera vez)
$ docker run --name mysql-9.7 -e MYSQL_ROOT_PASSWORD=admin -p 3306:3306 -d mysql:9.7

# las siguientes veces basta con arrancarlo
$ docker start mysql-9.7

Ejecútalos con Workbench, DBeaver o el CLI de MySQL. Si ya los corriste en una sesión anterior, sáltate esto.

  `id` int NOT NULL AUTO_INCREMENT,

Instalar jq

# macOS
$ brew install jq

Paso dos

02 Arrancar la aplicación

Desde la carpeta del proyecto, elige una de las dos formas. La primera es la de todos los días; la segunda genera el .jar ejecutable, que es lo que entregarías a producción.

# opción A — desarrollo, recompila al vuelo
$ ./mvnw spring-boot:run

# opción B — empaquetar y ejecutar el jar
$ ./mvnw clean package -DskipTests
$ java -jar target/cruddemo-0.0.1-SNAPSHOT.jar

Sabes que arrancó bien cuando ves estas dos líneas al final del log:

Tomcat started on port 8080 (http) with context path '/'
Started CruddemoApplication in 2.417 seconds

Abre una segunda terminal. La ventana donde corre la app se queda ocupada mostrando el log — no puedes escribir ahí. Todos los curl de esta guía van en una terminal nueva. Para detener la app: Ctrl + C en la primera.

Paso tres

03 Tu primera petición

La prueba de vida. Si esto responde, el trío completo funciona: tu terminal habla con Tomcat, Tomcat con Spring y Spring con MySQL.

$ curl -s http://localhost:8080/api/employees
[{"firstName":"Patrobas","lastName":"Filologo","email":"patrobas@gmail.com","id":1}]

Si te salió Connection refused, la app no está arriba — vuelve al paso 2. Cualquier otro error está en la tabla de errores comunes.

De dónde sale esa URL

No es arbitraria: cada tramo viene de un lugar concreto del código.

TramoSignificadoDónde se define
http://Protocolo, sin cifrar—
localhostTu propia máquina (127.0.0.1)—
:8080Puerto donde escucha TomcatDefault de Spring Boot
/apiPrefijo de toda la clase@RequestMapping("/api")
/employeesRuta del método@GetMapping("/employees")

La URL final es la suma de la anotación de la clase más la del método. Por eso es /api/employees y no solo /employees.

Guarda la URL en una variable

Para no repetirla treinta veces, guárdala en una variable de shell. Vive solo en esa terminal: si abres otra pestaña, ahí no existe.

$ BASE=http://localhost:8080/api/employees
$ curl -s $BASE | jq .

Sin espacios alrededor del =. Si escribes BASE = http://... bash intentará ejecutar un programa llamado BASE y fallará. Al usarla lleva $ delante: $BASE.

Paso cuatro

04 Anatomía de un comando curl

Todos los comandos de esta guía se arman con las mismas seis piezas. Entiéndelas una vez y ya no tienes que memorizar nada.

PiezaQué hace
-ssilent. Oculta la barra de progreso que si no ensucia la salida.
-X MÉTODOFuerza el verbo HTTP: GET, POST, PUT, PATCH, DELETE.
-H "..."Agrega una cabecera. La que usarás siempre es Content-Type: application/json.
-d '...'data. El cuerpo JSON que le mandas al servidor.
\ al final de líneaContinuación: «el comando sigue abajo». Es cosmético, todo cabría en una línea.
| jq .Pasa la salida a jq, que la indenta. El . significa «todo tal cual, pero bonito».

Tres detalles que valen oro

El $ del inicio no se escribe. En los bloques de esta guía el $ representa el prompt de tu terminal. Copias lo que va después. Los botones «Copiar» ya lo omiten por ti.

-d ya implica -X POST. Si mandas cuerpo sin especificar verbo, curl asume POST. Por eso en PUT, PATCH y DELETE el -X sí es obligatorio: sin él acabarías creando registros en lugar de actualizarlos.

-s también silencia los errores de red. Si el servidor está caído, curl -s no dice absolutamente nada y parece que no pasó nada. Cuando estés depurando usa -sS: la S mayúscula vuelve a mostrar los errores.

El header Content-Type no es decorativo

Sin -H "Content-Type: application/json", curl anuncia el cuerpo como application/x-www-form-urlencoded, que es el formato de un formulario HTML. Spring ve un @RequestBody esperando JSON, no sabe cómo convertirlo y devuelve 415 Unsupported Media Type. Es el error número uno de todo el que empieza con REST.

Comillas: simples por fuera, dobles por dentro

El JSON exige comillas dobles en sus llaves y valores. Las comillas simples de bash envuelven todo el bloque para que el shell no intente interpretar nada de adentro. Si inviertes el orden, bash se come las comillas del JSON y curl manda basura.

Ver el código de estado

El cuerpo de la respuesta por sí solo no te dice si la operación fue un éxito. Para verlo, agrega -w (write-out), que imprime una plantilla al terminar:

$ curl -s -w "\n[HTTP %{http_code}]\n" $BASE/1
{"firstName":"Patrobas","lastName":"Filologo","email":"patrobas@gmail.com","id":1}
[HTTP 200]

Otras variables útiles: %{time_total} (segundos que tardó) y %{size_download} (bytes recibidos). Si además quieres ver las cabeceras que devuelve el servidor, usa -i; para ver la conversación completa, -v.

No mezcles -w con | jq. La línea [HTTP 200] no es JSON y jq revienta con parse error. Usa uno o el otro.

Paso cinco

05 Las seis rutas

Una tarjeta por endpoint. Las respuestas que ves son reales, capturadas contra la app corriendo. Ejecuta cada comando y compara.

GET /api/employees findAll()

Lista todos los empleados. La petición más simple que existe: sin verbo explícito (GET es el default de curl), sin cabeceras y sin cuerpo.

$ curl -s $BASE | jq .
[
  {
    "firstName": "Patrobas",
    "lastName": "Filologo",
    "email": "patrobas@gmail.com",
    "id": 1
  }
]

Devuelve un array: fíjate en los corchetes [ ]. Aunque haya un solo empleado, sigue siendo una lista.

GET /api/employees/{id} getEmployee()

Trae un empleado concreto. El número del final entra al método como @PathVariable int employeeId.

$ curl -s $BASE/1 | jq .
{
  "firstName": "Patrobas",
  "lastName": "Filologo",
  "email": "patrobas@gmail.com",
  "id": 1
}

Devuelve un objeto suelto, sin corchetes. Si el id no existe recibes un 500 — ver rarezas del código.

POST /api/employees addEmployee()

Crea un empleado nuevo. Aquí aparecen por primera vez el header y el cuerpo.

$ curl -s -X POST $BASE \
  -H "Content-Type: application/json" \
  -d '{"firstName":"Ada","lastName":"Lovelace","email":"ada@gmail.com"}' | jq .
{
  "firstName": "Ada",
  "lastName": "Lovelace",
  "email": "ada@gmail.com",
  "id": 2
}

No mandes id. El método hace theEmployee.setId(0) antes de guardar, para forzar un INSERT en vez de un UPDATE. Aunque escribieras "id":99, lo pisa. Quien asigna el id real es el AUTO_INCREMENT de MySQL, y te lo devuelve en la respuesta: anótalo, lo necesitas para los siguientes pasos.

PUT /api/employees updateEmployee()

Actualiza un empleado por completo. Cambia el 2 por el id que te devolvió tu POST.

$ curl -s -X PUT $BASE \
  -H "Content-Type: application/json" \
  -d '{"id":2,"firstName":"Ada","lastName":"Byron","email":"ada.byron@gmail.com"}' | jq .
{
  "firstName": "Ada",
  "lastName": "Byron",
  "email": "ada.byron@gmail.com",
  "id": 2
}

La URL va pelona, sin /2. El id viaja dentro del JSON, porque la firma del método es updateEmployee(@RequestBody Employee) y no recibe ningún @PathVariable. Es una decisión de diseño de este curso; muchas APIs reales sí usan PUT /employees/2.

PUT reemplaza el objeto entero. Tienes que mandar los cuatro campos. Si omites email, se guarda como NULL en la base de datos. Para cambios parciales existe PATCH.

PATCH /api/employees/{id} patchEmployee()

Actualiza solo los campos que mandas. Aquí el id vuelve a la URL y el cuerpo lleva únicamente lo que cambia.

$ curl -s -X PATCH $BASE/2 \
  -H "Content-Type: application/json" \
  -d '{"lastName":"King-Noel"}' | jq .
{
  "firstName": "Ada",
  "lastName": "King-Noel",
  "email": "ada.byron@gmail.com",
  "id": 2
}

Por dentro funciona distinto a PUT: recibe el cuerpo como Map<String, Object> en vez de Employee, trae el registro actual de la base y le pega encima solo las llaves que mandaste con jsonMapper.updateValue(). Lo demás queda intacto — nota que firstName y email sobrevivieron.

Tiene una guarda de seguridad. Si incluyes "id" en el cuerpo, revienta a propósito con «Employee id cannot be modified». Pruébalo: es el comportamiento correcto, no un bug.

DELETE /api/employees/{id} deleteEmployee()

Borra un empleado. Id en la URL, sin cuerpo — y por lo tanto sin -H ni -d: no mandas contenido, así que no hay Content-Type que declarar.

$ curl -s -X DELETE $BASE/2
Deleted employee id - 2

Aquí no hay | jq ., y es a propósito: el método devuelve un String, no un objeto. La respuesta es texto plano, y si se lo pasaras a jq fallaría con parse error porque no es JSON válido.

El patrón, en una tabla

Todo lo anterior se resume en dos preguntas: dónde va el id y si hay cuerpo.

Verbo¿Dónde va el id?¿Cuerpo?Content-TypeDevuelve

GET unoURLnonoobjeto JSON

La regla que resume la tabla: si mandas cuerpo, necesitas el header Content-Type. Si no mandas cuerpo, no lo necesitas.

Paso seis

06 El ciclo CRUD completo

Ahora encadena todo en una sola sesión. Este es el ejercicio que debes poder hacer de memoria: crear, leer, actualizar, parchear y borrar, dejando la tabla como estaba al principio.

# 0 · define la variable y mira el estado inicial
$ BASE=http://localhost:8080/api/employees
$ curl -s $BASE | jq .

# 1 · CREATE — apunta el id que te devuelve
$ curl -s -X POST $BASE -H "Content-Type: application/json" \
  -d '{"firstName":"Grace","lastName":"Hopper","email":"grace@gmail.com"}' | jq .

# 2 · READ — sustituye 3 por TU id
$ curl -s $BASE/3 | jq .

# 3 · UPDATE total
$ curl -s -X PUT $BASE -H "Content-Type: application/json" \
  -d '{"id":3,"firstName":"Grace","lastName":"Murray Hopper","email":"grace.hopper@navy.mil"}' | jq .

# 4 · UPDATE parcial
$ curl -s -X PATCH $BASE/3 -H "Content-Type: application/json" \
  -d '{"email":"amazing.grace@navy.mil"}' | jq .

# 5 · DELETE y verificación final
$ curl -s -X DELETE $BASE/3
$ curl -s $BASE | jq .

El 3 es un ejemplo, no una constante. El id te lo asigna MySQL y va subiendo cada vez que creas un registro — aunque lo borres, el contador no retrocede. Usa siempre el que te devolvió tu POST. Si lo perdiste, recupéralo con un curl -s $BASE | jq .

Al terminar, el último GET debe mostrar exactamente lo mismo que el primero. Si sobró alguien, bórralo.

La versión automatizada

El proyecto incluye un script que hace este ciclo completo y verifica cada paso. Úsalo después de haberlo hecho a mano, para comparar tus resultados:

$ ./guias/test-endpoints.sh

Es idempotente: crea su propio registro de prueba, lo manipula y lo borra. Puedes correrlo las veces que quieras sin ensuciar la tabla.

Referencia

Si usas Windows

Los comandos de esta guía están escritos para bash y zsh (macOS y Linux). En Windows funcionan igual, pero hay tres trampas de las que nadie te avisa.

1. Escribe curl.exe, no curl

En PowerShell, curl es un alias de Invoke-WebRequest, que es otro programa distinto y no entiende -s ni -X. Si ves el error «A parameter cannot be found that matches parameter name 's'», es exactamente esto. La solución es llamar al ejecutable real por su nombre completo:

$ curl.exe -s http://localhost:8080/api/employees

2. Las comillas se comportan distinto

PowerShell y CMD se comen las comillas dobles del JSON antes de que curl las vea. En CMD, invierte las comillas y escapa las de adentro con \":

$ curl.exe -X POST http://localhost:8080/api/employees -H "Content-Type: application/json" -d "{\"firstName\":\"Ada\",\"lastName\":\"Lovelace\",\"email\":\"ada@gmail.com\"}"

3. La solución definitiva: el cuerpo en un archivo

En lugar de pelearte con las comillas, guarda el JSON en un archivo y pásaselo a curl con @. Esto funciona idéntico en Windows, macOS y Linux, y es lo que se hace en la vida real cuando el cuerpo crece:

# guarda esto como empleado.json
{"firstName":"Ada","lastName":"Lovelace","email":"ada@gmail.com"}

# y mándalo con @ delante del nombre del archivo
$ curl.exe -s -X POST http://localhost:8080/api/employees -H "Content-Type: application/json" -d "@empleado.json"

Alternativa cómoda: instala Git Bash o WSL y usa los comandos de esta guía tal cual, sin modificar nada. Es lo que recomiendo si vas a trabajar seguido con APIs.

Referencia

Rarezas del código que te van a confundir

Estos comportamientos son del proyecto tal como está en esta etapa del curso. No son fallas tuyas: si te topas con alguno, ya sabes por qué pasa.

Lo que observasPor qué pasa
Todos los errores son 500,
nunca 404		 Cuando un id no existe, el controlador lanza una RuntimeException y todavía no hay un @ControllerAdvice que la traduzca a un 404 decente. Se resuelve en la sección de exception handling.
Un PUT sin id
crea un duplicado		 updateEmployee() llama directo a save() sin validar nada. Si el id falta o vale 0, JPA hace un INSERT y acabas con un empleado de más en vez de recibir un error.
Un PUT borró un campo
que no toqué		 PUT es reemplazo total. El campo que omitas se guarda como NULL. Es correcto según la semántica de HTTP — para cambios parciales usa PATCH.
El POST ignoró
el id que mandé		 A propósito: addEmployee() hace setId(0) antes de guardar, para garantizar que siempre sea un alta y nunca una actualización accidental.
El PATCH rechaza
id en el cuerpo		 También a propósito. Es una guarda de seguridad explícita: la clave primaria no debe poder cambiarse desde una petición.
Los ids no se reciclan
al borrar		 El AUTO_INCREMENT de MySQL solo avanza. Si borras el id 5, el siguiente registro será el 6, no el 5.

Referencia

Errores comunes

Busca aquí el mensaje que te salió antes de preguntar. Casi todo lo que falla en esta práctica está en esta tabla.

MensajeCausaSolución
Connection refused La app no está corriendo, o la paraste sin darte cuenta. Vuelve a la terminal de la app y arráncala. Verifica con lsof -i :8080.
415 Unsupported Media Type Mandaste cuerpo sin declarar el tipo. Agrega -H "Content-Type: application/json".
400 Bad Request El JSON está mal formado: una coma de más, una comilla faltante, comillas curvas copiadas de Word. Revisa el cuerpo carácter por carácter. Escribe las comillas a mano, no las pegues de un procesador de texto.
500 en un GET o DELETE Ese id no existe en la tabla. Lista todos con curl -s $BASE | jq . y usa un id real.
Communications link failure MySQL no está arriba, o el contenedor se detuvo al reiniciar la máquina. docker start mysql-9.7 y vuelve a arrancar la app.
jq: parse error Le pasaste a jq algo que no es JSON: la respuesta de DELETE, o la línea que agrega -w. Quita el | jq . en DELETE, y no combines -w con jq.
Port 8080 was already in use Dejaste otra instancia de la app corriendo en otra terminal. Ciérrala, o encuentra el proceso con lsof -i :8080 y termínalo.
No sale absolutamente nada -s silenció el error de red. Repite el comando con -sS para ver qué pasó realmente.

Ejercicios

Resuélvelos en la terminal y entrega los comandos que usaste junto con la respuesta que recibiste.

  1. Alta múltiple. Crea tres empleados distintos y luego lista la tabla para comprobar que están los tres. ¿Qué ids les tocaron?
  2. PATCH quirúrgico. Cambia solo el email de uno de ellos. Demuestra con un GET que su nombre y apellido no se movieron.
  3. Rompe el PUT a propósito. Manda un PUT omitiendo el campo email. Consulta después ese empleado y explica en una frase qué pasó y por qué.
  4. El id que no fue. Haz un POST incluyendo "id": 999 en el cuerpo. ¿Qué id te devolvió el servidor? Busca en EmployeeRestController.java la línea exacta que lo explica.
  5. Solo el status. Consigue el código de estado de cada operación sin ver el cuerpo de la respuesta. Pista: combina -o /dev/null con -w.
  6. Limpieza. Borra los tres empleados que creaste y deja la tabla exactamente como la encontraste.
  7. Reto. Escribe tu propio script de bash que haga el ciclo CRUD completo y capture el id del POST automáticamente, sin que tú lo escribas a mano. Pista: jq -r '.id'.
